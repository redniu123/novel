- 当前状态：`pending_design_review`
- 工作分支：`feature/TASK-005-generation-quality-loop`
- 前置依赖：TASK-001B、TASK-002、TASK-003A/003B、TASK-004 已完成代码交付

## 2. 背景

当前系统已经具备建书、规划、上下文编排、正文生成、自动审查、有限修订、状态结算、
结构化故事状态、SQLite 记忆、人工审核和成本账本。真实模型只验证过建书和单章主链，
体验期额外生成过第 2 章，但尚未证明同一本书可以稳定连续生成 20-30 章。

TASK-004 之后的原建议偏向商业入口、暂停恢复、权限和成本报表。这些能力不能回答当前
最重要的问题：现有生成系统能否持续写出可读、连贯、可人工接管的走量小说。因此用户
在 2026-07-23 决定把真实连续生成和质量观察提升为下一任务。

## 3. 冻结原则

> 先完整生成并观察，拿到真实缺陷后再改生成系统，不预先假设问题出在 Prompt、模型
> 还是记忆层。

该原则具体约束为：

1. 基线运行期间固定书籍简报、模型、模型路由、生成参数、审查模式和修订次数。
2. 不因单章主观不满意而中途改 Prompt、模型、上下文选择、记忆、审查规则或状态逻辑。
3. 每个缺陷先记录可观察证据、首次出现章节、重复次数和影响，再提出根因假设。
4. “模型问题”“Prompt 问题”“记忆问题”均不得仅凭阅读感受定论。
5. 先完成基线或触发冻结的安全/完整性停止条件，再进行跨章归因和优先级排序。
6. 修复必须另有明确子任务、允许修改面、验收标准和基线对照，不在观察轮顺手修改。

## 4. 总目标

1. 在被 Git 忽略的隔离项目中创建一本新的走量网络小说。
2. 使用固定配置，目标连续生产前 20 章；20 章是 ADR-001 的最低成功门槛。
3. 生成过程按 `1-3`、`4-10`、`11-20` 三个观察窗口记录，但窗口之间不调参。
4. 记录生成成功率、耗时、token、字数、审查、修订、状态、连续性和人工修改量。
5. 建立章节级缺陷台账和跨章缺陷聚类，区分事实、症状、假设和已证实根因。
6. 形成按用户价值和复现频率排序的生成缺陷清单。
7. 基于证据决定是否以及如何修改生成系统，并为选中的缺陷创建后续子任务。
8. 在基线中一并取得 TASK-003 真实模型人工验收可复用的证据；无法覆盖的项目单列，
   不伪造验收完成。

## 5. TASK-005A 基线范围

TASK-005A 只负责可重复运行、观察和报告，不负责修复生成质量问题。

### 5.1 运行路径

- 使用 InkOS 已有完整章节管线，每次只执行一章。
- 关闭 daemon，不使用 `auto`，不使用 `write next --count > 1`。
- 默认从官方 CLI `write next <book-id> --count 1` 进入，以避免为了实验重写生成链。
- 商业 Orchestrator 尚无 CLI/Studio 正式入口。TASK-003 人工验收需要的商业入口证据使用
  独立、最小且可复现的实验适配器或现有公开 API 取得，不与 20 章正文基线混淆。
- 如果需要实验适配器，只允许组合公开 API；不得复制 Planner、Writer、Auditor、
  Reviser 或 Runner 内部逻辑。

#### 5.1.1 方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 官方 CLI 逐章生成 | 已有真实模型证据；不新增生成行为；最容易完成 20 章 | 不经过商业状态和成本 Recorder | 作为 20 章生成质量基线 |
| B. 商业 Orchestrator 逐章生成 | 同时验证 TASK-003/004；具备商业状态和账本事件 | 尚无正式用户入口；一旦暂停没有恢复能力，可能过早截断长距离样本 | 仅用于独立 TASK-003 验收证据 |
| C. 先新增正式商业 CLI/Studio 入口 | 使用体验完整 | 会把入口治理和新行为混入基线，扩大变量与范围 | 本任务拒绝 |

采用 A/B 分轨而不是混用：A 回答“现有 InkOS 生成链能否连续写 20 章”，B 回答
“商业包装是否符合 TASK-003 验收”。两者使用独立隔离项目，证据不得互相冒充。

### 5.2 观察窗口

| 窗口 | 章节 | 目的 | 是否允许调参 |
| --- | --- | --- | --- |
| A | 1-3 | 验证基础链路、记录早期角色和冲突建立 | 否 |
| B | 4-10 | 观察节奏、重复、人物和短中程连续性 | 否 |
| C | 11-20 | 观察长距离记忆、伏笔、状态漂移和累积退化 | 否 |

窗口检查不是发布批准，也不是修改系统的入口。检查结果只追加到观察记录。

### 5.3 每章自动记录

- 章节号、标题、最终字数和 pipeline status；
- 生成开始/结束时间和是否成功；
- 自动审查 issue 的 severity、category 和数量；
- 是否触发自动修订以及最终修订次数可取得的证据；
- length telemetry、token usage 和状态结算结果；
- 当前人物/地点/关系/资源/时间/伏笔摘要的结构完整性；
- 错误阶段、稳定错误码和是否可以安全继续。

### 5.4 每章人工观察

用户是最终内容判断者。人工表至少记录：

- 开篇吸引力、剧情推进、冲突强度和章末钩子；
- 人物动机、性格、能力、关系和知情边界是否一致；
- 时间、地点、资源、世界规则和因果是否连续；
- 伏笔是否建立、推进、遗忘、误回收或重复建立；
- 是否出现剧情循环、信息重复、模板化表达或明显水文；
- 自动审查是否漏报、误报，自动修订是否实质改善；
- 为达到可发布标准所需的人工修改分钟数和修改比例区间。

质量评分只用于同一本基线内比较，不宣称是跨题材的客观文学评分。

## 6. 缺陷记录与归因

每条缺陷至少包含：

- 唯一编号和简短标题；
- 首次出现章节、再次出现章节和出现频率；
- 原文位置或本地证据路径，不把正文提交 Git；
- 可观察症状及对阅读/生产的影响；
- 当时输入、状态摘要、审查结果和相关配置快照；
- 候选归因：规划、上下文编排、Writer、Auditor、Reviser、状态结算、检索记忆、模型、
  配置或未知；
- 支持与反驳每个候选归因的证据；
- 当前结论：`untriaged`、`hypothesis`、`confirmed` 或 `disproved`；
- 严重度：Blocker、Major、Minor、Suggestion。

没有对照实验或稳定代码路径证据时，根因保持 `hypothesis`，不得写成已确认事实。

## 7. 停止条件

以下情况暂停继续调用模型并保留现场：

1. 密钥、完整模型请求/响应或小说正文可能进入 Git、日志或聊天。
2. 故事权威状态、章节索引或 SQLite 出现无法安全读取的损坏。
3. 章节号漂移、覆盖既有章节或跨书数据污染。
4. 同一运行出现无法确认是否仍在后台继续的超时/并发状态。
5. 模型服务认证或计费配置异常。
6. 连续三次同类管线失败，且继续调用只会重复消耗而不能增加新证据。

普通质量下降、审查 warning 或单章主观不满意不是中途调参理由，应继续记录到下一个
观察窗口。若硬停止使 20 章未完成，TASK-005A 必须如实标记失败或阻塞，不能把较短样本
宣称为连续生产成功。

## 10. 禁止修改范围

在基线缺陷完成归因和用户批准具体修复任务前，不得修改：

- Prompt 和提示词模板；
- 模型、Provider、API 格式和模型路由实现；
- Planner、Writer、Auditor、Reviser 行为；
- PipelineRunner 阶段、重试、审查和状态结算逻辑；
- 上下文选择、记忆检索、故事权威状态或 SQLite Schema；
- TASK-003/004 冻结 Schema 和语义；
- CLI、Studio、daemon、Scheduler 的商业入口治理；
- 依赖、锁文件、许可证和自动发布能力。

基线运行参数的冻结不等于修改这些实现。

## 11. 数据与安全边界

- 小说工程固定在仓库 `tmp/` 下的被忽略目录，按单一 `bookId` 隔离。
- 不提交小说正文、创作简报原文、数据库、章节状态、模型响应、日志、密钥或价格表。
- Git 只保存不含正文的任务设计、聚合结果、缺陷元数据和脱敏结论。
- 引用正文证据时只记录本地路径、章节号和必要的短摘要；不得把大段正文复制进 Git。
- 每个观察窗口结束后执行 `git status` 和 `git check-ignore` 安全检查。
- TASK-004 成本账本可作为观测来源，但成本能力不是本任务的开发目标。

## 12. 验收标准

TASK-005 总任务的首个里程碑（TASK-005A）至少满足：

1. P1-P10 经用户确认并记录，基线期间没有静默变化。
2. 新隔离小说完成建书，故事规划和初始状态可读取。
3. 逐章执行，不使用后台批量生成；daemon 始终关闭。
4. 完成 20 章，或按第 7 节准确记录硬停止及现场证据。
5. 三个观察窗口都有配置快照、自动指标和人工观察记录。
6. 章节号、故事状态、投影和 SQLite 没有跨书污染或静默损坏。
7. 至少输出一份跨章缺陷聚类；没有缺陷时也必须说明检查证据。
8. 事实、症状、假设和已确认根因在报告中明确分开。
9. 基线运行期间没有修改生成系统行为。
10. 小说正文、运行数据和凭证未进入 Git。
11. TASK-003 人工验收能复用的证据逐项映射，未覆盖项如实保留。
12. 用户确认优先缺陷后，才创建第一个生成修复子任务。

## 13. 验证方案

设计轮：

- Markdown 链接和状态一致性检查；
- `git diff --check`；
- `.gitignore` 白名单与运行数据忽略检查；
- 不运行模型、不产生小说数据。

TASK-005A：

- 运行前执行现有精确回归或至少 core/CLI typecheck 与相关测试；
- 每章执行一次完整管线并保存本地结果；
- 每个窗口核对章节索引、结构化状态、Markdown 投影和 SQLite；
- 运行后执行观测工具测试、聚合一致性检查和 Git 安全检查；
- 若新增实验适配器或观测工具，必须有自动测试且不得改变默认 CLI 行为。

## 14. 回滚方案

- 设计轮只删除新增任务/ADR并恢复索引和当前状态说明。
- 观测工具或实验适配器可独立删除，不影响原版 InkOS 生成链。
- 本地实验项目不自动删除；先保留缺陷证据，用户确认归档后再清理。
- 不通过回滚删除或覆盖故事权威状态来掩盖基线失败。

## 15. 非目标

- 在观察前优化 Prompt、模型选择、记忆或审查规则；
- 商业入口统一治理、暂停恢复、审核权限或成本报表；
- 多本并行、自动发布、平台账号和读者反馈闭环；
- 用自动评分替代人工阅读；
- 用一两章成功推断 20-30 章稳定；
- 在同一次基线中进行 A/B 模型或 Prompt 对比。
